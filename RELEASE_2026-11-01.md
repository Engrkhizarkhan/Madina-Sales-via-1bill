# Client demo and ticket-page controls — 1 November 2026

Roster schedules can be edited and deleted even when dated tickets exist. Edits keep existing departure snapshots intact; deleting removes the schedule from working/public lists and stops future sales while retaining tickets, refunds, manifests and ledger references. Bus-layout, route and crew deletion also removes the setup record from working lists without erasing referenced history. Confirmation dialogs explain the effect.

Start boarding is removed from the roster. The ticket page provides Pause / Resume seats, Bus gone / close tickets, confirmed release of unpaid reservations, Record return, and a confirmed counter-sales reopening with a required reason. Reopening is audited and does not reopen the public website. Dispatcher accounts retain departure and vehicle controls, with ticket issuance and voucher writes restricted to counter/management.

Bus setup now contains a reusable bus name, service class and seat capacity. Registration number, model-year, maintenance status and Next service inputs are removed. Actual vehicle number is entered on the ticket page; counter sales require that saved assignment. Public paid tickets can precede assignment and update when a vehicle is saved.

The voucher is a keyboard-accessible collapsed disclosure by default. Seat maps have Refresh seats, an update timestamp/error, and five-second automatic refresh across sessions. Backend unique active-seat constraints continue to prevent conflicting sales. Stale refresh responses cannot overwrite a locally completed mutation.

Public checkout issues one paid simulated 1Bill ticket per seat in PAYMENT_MODE=demo, with server-generated DEMO payment references. Customer and operator screens use standard booking labels. Internal payment references retain their original environment markers for reconciliation. Other modes reject web checkout until the real 1Bill adapter is configured; the browser cannot force a paid transaction or create an unpaid web hold. Counter reservations continue to work.

Finance includes payment-method and ticket-status donut charts, net revenue bars by route and the existing daily column chart, all tied to date filters. The operator-only client-demo script replaces operational records with synthetic route, bus, crew, ticket, refund and expense data dated around the current Pakistan date. It preserves all existing login accounts and sessions, requires explicit runtime flags, and is never run by normal migrations.

Validation: production build, lint, syntax checks, 84 API checks, 57 counter workflow checks, 8 layout/date checks; disabled-gateway rejection; repeated idempotent migration application. Browser checks cover simplified bus creation, voucher collapse/expand, pause/resume locking, removal of roster boarding controls, separate paid web tickets/tokens and cross-session automatic seat updates. Desktop/mobile finance and counter layouts and four printed receipt/token pages are visually checked. All functional tests use an isolated MySQL database.

Before the explicitly requested initial live data reset, preserve database/source/web backups, stop the API, migrate, apply PAYMENT_MODE=demo and seed synthetic records; then start the existing PM2 service and verify live assets, database reconciliation and preserved account credentials. No dependencies were added.

Presentation follow-up: removed environment captions/badges from website, checkout, dashboard, settings and printed slips. Stored seed metadata and references use operational display labels in finance, reports and exports while raw backend/audit values remain intact. The follow-up deployment does not reset or alter existing bookings. Payment processing remains in the existing simulated mode pending merchant configuration.
